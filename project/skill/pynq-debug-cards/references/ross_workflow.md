# ROSS / Vivado MCP 协作工作流

ROSS 的 Vivado MCP 将模型连接到正在运行的 Vivado 会话，用于执行 Tcl、读取日志以及组织综合、实现与检查。本技能包在这条工具链上提供任务选择、执行状态核对和结果验收方法：`pynq-debug-cards` 按症状选择处理路径，`pynq-pl-preserve` 为适用的 RTL 改动生成行为对照及验证收据。

接入方式是让模型读取 Skill 后使用现有 ROSS 工具，并运行包内脚本生成的 Tcl。以下流程复用已交付的卡片和检查器；会话工具名称、参数及执行主机路径按当前 ROSS 实例的 schema 读取。

## 1. 执行前：确定对象、版本与检查目标

1. 记录板卡/器件、Vivado 版本、工程路径、top、待执行阶段和输出目录；从当前回执取得真实 session 与任务身份。
2. 核对该会话的当前工程和忙闲状态。同一工程沿原会话顺序执行；独立实验使用各自会话与输出目录，避免混用工程状态和日志。
3. 根据症状只读取相关卡片组。命令或选项被拒绝时先核对 schema 和本机帮助；引用缺失时检查实际文件集、include 与初始化文件。
4. 在执行前约定完成条件：功能输出、仿真结束标志、资源/时序结果，以及正式产物的配对身份。

| 任务或症状 | 读取的卡片 | 形成的执行约束 |
| --- | --- | --- |
| 阶段变化、判重、会话或参数问题 | [E01–E04：工具调用](tools.md) | 绑定真实会话、阶段与输入，按当前版本提交 |
| 文件集、BD 传播、HWH/XSA 或 IRQ 问题 | [E05–E08、H20：构建与制品](artifacts.md) | 核对实际工程引用、接口和同次构建来源 |
| 启动、依赖或入口问题 | [E09、E10、E12、H13、H14：启动连接](startup.md) | 区分工具可达、进程启动和业务 READY |
| DMA、共享设备、异步请求或 MMIO 问题 | [E11、H15、H16、H19：资源交接](handoff.md) | 沿原 owner 收敛在途工作，再恢复目标请求 |
| 最新输入与消费边界问题 | [H17、H18：实时输入](input.md) | 分开记录观察与消费，保留最新状态及来源时间 |

这些卡片适用于对应的工程条件。示例中的寄存器、接口、超时与实例身份由目标工程的实际配置替换。

## 2. 执行中：跟踪原任务并解释回执

长时间综合或布线提交后，保存工具返回的任务句柄，沿同一个操作读取状态与增量日志。运行中的回执表示工作仍在执行；新阶段需要新的阶段身份，并以新的完成标志与产物确认实际执行。

结果按三个层次核对：

| 层次 | 核对内容 | 下一步 |
| --- | --- | --- |
| 工具调用 | 请求是否被接受，是否仍运行，会话/任务是否匹配 | 续接原句柄或修正调用参数 |
| 命令执行 | Tcl 返回码、完整日志、实际执行阶段、输出路径 | 按具体诊断定位文件集、参数或运行步骤 |
| 工程结果 | 仿真断言、预期结束、像素/协议输出、实现报告、产物身份 | 完成目标检查后再进入下一阶段 |

项目调用记录中曾出现阶段切换后的重复判定、已有计划绑定到其他会话、命令退出正常而领域检查尚未通过、参数在当前版本被拒绝等情况。E01–E04 将这些观察转化为有明确完成条件的处理步骤；对应记录见[技术摘要](../sources/preflight_cards.txt)、[调用观察目录](../sources/preflight_catalog.txt)及[逐卡来源](../origins.json)。[GPU 集成复验摘录](../sources/ross_mcp_cases.json)保留三组实际会话的命令、原生诊断、修订与完成结果，供按症状追溯。

## 3. 验收：让工具执行对应可检查的设计结果

### 3.1 保持周期行为的 RTL 改动

适用对象是单时钟、自包含的行为级叶模块。先冻结原版，以未修改候选校准实例和参数，再对目标候选运行相同激励。

在包含 `skill/` 的项目目录执行以下开发 PC 命令，输出目录须为新目录：

```powershell
python -X utf8 -B skill/pynq-pl-preserve/scripts/preserve.py build skill/pynq-pl-preserve/examples/config.json --out build/output/ross_preserve_01
$runPath = (Resolve-Path build/output/ross_preserve_01/run.tcl).Path.Replace('\', '/')
Write-Output "source {$runPath}"
```

第一步生成参考模块、全输出监视器、输入摘要和 `run.tcl`；第二步输出可提交的 Tcl 命令。将该命令通过 ROSS 当前提供的 Tcl 执行入口，送入**单独的空闲 Vivado 会话**。生成脚本会创建并关闭仿真工程，已有综合/布线任务继续使用其原会话；执行主机与生成脚本的主机不同则先传输输入，再在执行主机重新运行 `build`，生成该主机上的路径与输入摘要。

仿真结束后在同一项目目录执行：

```powershell
python -X utf8 -B skill/pynq-pl-preserve/scripts/preserve.py verify build/output/ross_preserve_01
```

预期输出 `PRESERVATION_UNDER_SUPPLIED_STIMULUS_PASS` 并生成 `verified.json`。校验器逐项核对源文件与生成文件摘要、原测试结束标志、实际 `$finish`、所有实例的比较结果、复位/活动样本和运行诊断。日志保存在输出目录的 `simulation/` 下。实际模块的完整实验与故障变体命令见[验证入口](../../validation/README.md)。

### 3.2 选择与改动相匹配的检查

| 改动目标 | 合适的检查 |
| --- | --- |
| 输出及周期行为保持不变的资源重构 | `pynq-pl-preserve` 全输出比较，随后检查综合/实现资源与时序 |
| 增加流水或调整延迟、但保持功能结果 | 按新时序合同检查有序输出、像素写入、CRC 与完成条件；比较同输入周期 |
| 完整 Overlay、跨时钟或子 IP 集成 | 对应层级的仿真、时钟与约束分析、完整实现和接口检查 |
| 正式 bit/HWH/XSA 导出与部署 | E06/H20 的同次构建、配置负载与接口配对，接续项目标准部署验收 |

`pynq-pl-preserve` 目前覆盖单时钟、自包含叶模块及所给激励下的周期行为。对有意改变接口或周期的优化，按新的合同选择检查方式，可以保留相同的“冻结输入—独立参考—完整日志—验收收据”组织方法。

### 3.3 已验证能力与可复用收益

实际上传模块的受控实验中，原版与内部寄存器重命名变体通过，CRC 复位值变体在 5.001 ns 定位到 `completed_crc32` 差异；迁移目录后六次仿真均符合预期。故障变体的单项 verify 返回非零，是该用例预期的检出结果，由实验汇总器统一判定。证据见[技能报告](../../report.md)与[迁移回执](../../validation/evidence/delivery_replay/result.json)。

在 ROSS 工作流中，卡片帮助模型选择下一次工具操作和收口条件，脚本则自动完成参考连线、输出比较和日志判定。可复用的成果是明确的会话/阶段身份、完整输入绑定、具体差异定位及可追溯收据；综合与布线工具继续提供硬件资源和时序结论。

## 4. 一次任务应保存的结果

- 工具与工程版本、任务阶段、当前会话和输出目录。
- 冻结参考、候选、测试台及生成输入的摘要。
- 原始执行日志、实际结束标志及领域检查结果。
- 适用时的资源/时序报告，以及正式 bit/HWH/XSA 配对结果。
- 本次结论、下一步及仍需执行的目标层级验证。

项目公开案例使用与工程问题有关的调用节选和诊断字段；个人路径、连接凭据和无关对话在整理时移除。方法迁移时使用新工程的真实参数和来源身份。

ROSS 工具接入参考 AMD 官方 [Vivado MCP 文档](https://github.com/Xilinx/ross-ai-assistant/blob/main/docs/getting-started/vivado-mcp.md)。
