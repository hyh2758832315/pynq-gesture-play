# 重绘用技术说明与数据口径

## 图 01：最新状态消费与调度

### 数据与身份

视觉输入包含手势分类、frame_id、run_id、config_epoch、原始 source_at 和观察时间。读取当前快照不会刷新 source_at。逻辑槽保存最新观测，后续状态覆盖较早状态。

| 情况 | 调度行为 | 图上表达 |
|---|---|---|
| 输入来源身份一致且仍新鲜，控制器 READY_IDLE | 进行姿态变化检查 | 正向箭头 |
| 控制器 MOVING | 保存最新候选与可消费帧标记，暂不提交动作 | 忙窗口上方的状态槽 |
| 到达 t 且当前动作执行完成 | 重新读取/评估仍有效的最新状态 | t 边界连接下一动作 |
| 最新姿态等于最后已批准姿态 | 继续保持，不重播 | 同态保持 |
| 有手但暂未分类（合格输入的 None） | 保持已批准状态 | 不画成 default |
| 明确无手/default | 下发默认目标，不另占一个 t | default 无额外等待 |
| 来源缺失、过期或身份变化 | 交给外层 owner 的恢复/交接流程 | 可选旁路，不伪造新鲜手势 |

示例从 0 时刻批准握拳，到 t₁ 变张手、t₂ 变剪刀。t 边界若输入仍有效且控制器空闲，下一动作使用剪刀，期间张手不会补播。t 是批准起算的调度窗口；串口操作、取消和实际控制器就绪仍参与边界判断，不画成无条件精确的硬件定时中断。

依据：`gesture_consumer.py` 的 `tick` / `ready_frame` / `last_sent`，`controller.py` 的 `approved_at` / `ready_at`，`motion.py` 的固定播放路径；启动入口选择合格手势与持续 owner。

## 图 02：低负荷通信如何实现

PS 独立动作进程通过 USB 串口调用 SDK，逐电机 ID 操作。图中电机 ID i 的泳道表示可重复到配置的 17 颗电机。底层连接不画成 PL 的 17 路 PWM。

1. **启动**：载入模型与标定、连接、读取检查、受控使能。READ 从地址 `0x10` 读取 48 字节寄存器块；启动图概括这些步骤，不表示只发生一条 READ。
2. **预计算**：关节姿态经标定/传动映射转换为电机角度，`raw = round(angle / POS_SCALE)`；`POS_SCALE = 2π/4096 rad/count`，检查 raw 在 0..4095。预编译元组为 `(motor_id, raw, speed)`。
3. **播放阶段**：张手、握拳含 default、中点、目标阶段；剪刀含 default、目标。中点主要涉及指尖关节，不应画成所有关节一律二等分。
4. **写入**：逐 ID 调用 `WritePos(id, raw, 0, speed)`。与目标缓存中的 `(raw, speed)` 相同则跳过；成功应答后更新缓存，异常清空缓存。
5. **等待**：可取消的事件等待让出 CPU；正常播放不持续 READ 位置。ACK 表示通信/设备状态，`played` 表示播放过程完成，均不是实测机械到位。
6. **退出**：逐 ID 写 torque=0，之后逐 ID 读回确认 OFF，关闭串口、释放锁。图 02 将每类事务概括成一组箭头，真实 release 代码先完成所有 ID 的写，再完成所有 ID 的读。

`BoundedPortHandler` 使用有界事务和可取消检查。配置默认 wait_slice=0.01 s、transaction_timeout=0.1 s；这是代码配置，不是性能实测。不要把串口等待绘制为紧循环持续占用 CPU。图中可保留“同一 owner/会话复用”，避免画出多个并行控制者争抢同一端口。

## 图 03：编码、校验与应答

### 通用帧格式

| 帧 | 字节顺序 | 长度规则 |
|---|---|---|
| 指令 | FF FF / ID / LENGTH / INSTRUCTION / PARAMETERS / CHECKSUM | LENGTH = 参数数量 + 2；总长 = LENGTH + 4 |
| 状态 | FF FF / ID / LENGTH / ERROR / DATA / CHECKSUM | LENGTH = 数据数量 + 2；总长 = LENGTH + 4 |

校验和：`(~sum(bytes_from_ID_through_last_parameter_or_data)) & 0xFF`。接收端可验证从 ID 到 checksum 的所有字节之和模 256 等于 255。

### 13 字节位置命令

示例 ID=1、raw=2048、time=0、speed=500：

| byte | HEX | 名称 | 说明 |
|---:|---|---|---|
| 0 | FF | HEADER0 | 帧头 |
| 1 | FF | HEADER1 | 帧头 |
| 2 | 01 | ID | 电机 1，单播 |
| 3 | 09 | LENGTH | 7 个参数 + 2 |
| 4 | 03 | WRITE | 写指令 |
| 5 | 2A | ADDRESS | 连续数据起始寄存器 42 |
| 6 | 08 | POS_H | 位置高字节 |
| 7 | 00 | POS_L | 位置低字节 |
| 8 | 00 | TIME_H | 时间高字节 |
| 9 | 00 | TIME_L | 时间低字节 |
| 10 | 01 | SPEED_H | 速度高字节 |
| 11 | F4 | SPEED_L | 速度低字节 |
| 12 | CB | CHECKSUM | `~0x0134 & 0xFF` |

完整 TX：`FF FF 01 09 03 2A 08 00 00 00 01 F4 CB`。

成功 ACK：`FF FF 01 02 00 FC`。这里 LENGTH=2、ERROR=0、无位置数据。

当前 `scscl` 构造 `scs_end=1`，16 位数据高字节在前。SDK 的辅助函数 `scs_lobyte` 在此模式下返回高字节；常量/函数名字中的 L/H 不等于线序。SCSCL 对应当前实测编码；不能直接换成 STS/SMS 的默认字节序。

raw=2048 是电机编码器目标计数，经传动/标定后不等于某个手指关节直接旋转 180°。speed=500 为此接口的原生速度字段，不标成 500 Hz 或 500 rpm。

### 其余示例

| 操作 | 指令 HEX | 成功应答 |
|---|---|---|
| 读 ID 1 的 0x10 起 48 字节 | `FF FF 01 04 02 10 30 B8` | 54 字节，数据随设备而变 |
| 写 ID 1 的 torque(0x28)=0 | `FF FF 01 04 03 28 00 CF` | `FF FF 01 02 00 FC` |
| 读 ID 1 的 torque(0x28)，1 字节 | `FF FF 01 04 02 28 01 CF` | 为 0 时：`FF FF 01 03 00 00 FB` |

这些额外报文由同一长度与校验规则构造，并非实板抓包。`packet_check.json` 中的位置例子另经过本地真实 SDK + 内存串口调用核对。

寄存器：0x28 torque，0x2A 位置目标，0x2C 时间，0x2E 速度。正常位置写连续写入 6 字节。接收侧检查帧头、ID、长度、校验和和设备 error；异常交由 owner 处理。

SDK 中 ERROR 位定义：0x01 输入电压、0x02 角度传感器、0x04 过热、0x08 过电气、0x20 过载。其它位不扩展猜测。`COMM_SUCCESS=0` 表示通讯成功，设备 `error=0` 也必须满足；超时/损坏分别有独立通信错误码。

### 理论线时间

1 Mbaud、8N1 按每字节 1 start + 8 data + 1 stop = 10 bit 计算。13 B TX + 6 B ACK = 19 B，因此纯串行线时间下限 190 μs。这个数不包含 USB、设备处理、收发间隔和 PS 调度；不得标成动作起步或手势到位延迟。

## 图 04：对比数据及复算

### 上半区：历史 PYNQ 板测

| 记录 | 路径 | 动作段墙钟 s | 动作段 CPU s | 单核等效 % |
|---|---|---:|---:|---:|
| H143 | 插值写入 | 6.600283166 | 3.654565627 | 55.369830886 |
| H150 | 阶段目标 | 9.148883426 | 1.655558002 | 18.095738298 |

数据源是各 JSON 的 `phases.motion`。CPU%=CPU时间/墙钟时间×100；单核=100%，不是占整颗双核芯片的百分比。每轮包含 default、张手、剪刀、握拳各一次。各轮真实起点、等待及审计配置不同，属于历史阶段观测，不做严格配对的因果提升百分比。CPU 时间与墙钟时间同时保留，展示软件负担和等待策略的区别。不是最终 v3.0 完整系统占用。

内存：H143 有单独的 rss_max_kb，但其它两轮缺少同口径配对项，所以未画 RSS 对比。要增加内存或最终版 CPU，需要同版本、同输入、同动作比例与同采样窗口重新采集。

### 下半区：固定播放的同用例通信计数

筛选 `verification-final.json.fixed_playback_budget.results` 中 start=`default`，四个 state 各取 `skip_unchanged=False/True`。每例独立初始化、每个目标连续调用 Motion.run 两次。该测试直接调用底层播放，不经过上层同态保持门控。

| 两次播放的目标 | 全量写 | 跳过未变目标 |
|---|---:|---:|
| default | 34 | 17 |
| 张手 / paper | 102 | 44 |
| 剪刀 / scissors | 68 | 65 |
| 握拳 / rock | 102 | 75 |
| 四独立用例汇总 | 306 | 201 |

计数来自 SDK 内存串口，动作段均无寄存器 READ，单播 ACK 保留。启动、使能与卸力排除。报告中的 simulated_seconds 使用假时钟与合成等待，数据图没有采用这项动作时间。

- 写包减少：`(1 - 201/306) × 100% = 34.3137%`。
- 报文总量：`写包数 × (13 + 6)`，即 5,814 → 3,819 B；图中 kB 使用 1,000 B。
- 理论线占用：`字节数 × 10 / 1,000,000 × 1,000 ms`，即 58.14 → 38.19 ms。
- 写包与理论线占用收益绑定这四个独立用例，不外推成机械加速、整机 CPU 或全应用收益。

## 建议的精简讲稿

“手势输入只保留最新状态，忙时不积压动作。动作目标提前换算，播放时按阶段下发，跳过未变化的目标，等待期间让出 CPU。指令仍逐个电机检查应答，退出还会读回卸力状态。数据图分别给出历史板测的 CPU 与耗时，以及同用例离线写包计数，展示减少重复处理与通信的具体效果。”
