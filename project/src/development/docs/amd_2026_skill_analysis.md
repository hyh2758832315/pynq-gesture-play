## 2. 核心结论

参赛技能包采用两层结构：以通用 PYNQ 工程能力为主，以游戏设计、测试与 Studio 开发 Skill 为辅助。

通用层提炼 Overlay 预检、接口契约、DMA 与缓存、资源生命周期、黄金参考和证据采集；项目应用层展示这些能力如何支撑确定性游戏开发、同包测试、部署与界面验收。

ROSS 提供官方 Agent Skills、工具调用和文档检索基础。我们的贡献通过新增规则、适用边界、独立入口、失败测试与复用结果呈现。每项材料清楚区分 AMD 上游内容和本队新增内容。

游戏设计 Skill 可以作为参赛技能包的一小部分。其评价依据是相同框架下新玩法、新游戏项目的可复用方法与效果；通用 PYNQ 额外加分则围绕 PYNQ 共性流程的跨题目和跨板卡适用性举证。

## 4. 从项目记录到可复用 Skill

推荐采用以下提炼链路：

> 原始失败或观察 -> 触发条件 -> 诊断步骤 -> 修复或处理规则 -> 可执行检查 -> 复验结果 -> 适用边界。

| 层次 | 以邻接 XSA 解析问题为例 |
| --- | --- |
| 原始事实 | 在特定 PYNQ 3.1 环境中，邻接同 stem XSA 导致 bit 路径进入错误解析分支 |
| 根因依据 | 检查实际解析器源码和调用栈，确认错误发生在下载之前 |
| 方法提炼 | 校验完整制品身份；构造独立 bit/HWH 运行配对；让临时目录与 Overlay 同寿命 |
| 自动检查 | 正常配对、哈希不符、邻接 XSA、初始化失败清理等路径的检查与测试 |
| 适用范围 | 已确认的 PYNQ 版本和解析器行为；其他版本先执行能力检查 |
| 复用场景 | 图像处理、音频处理、采集或控制类 Overlay 的部署预检 |

通用化保留方法，配置化板卡与项目差异。文件路径、IP 实例、寄存器语义、时钟、DMA 模式和硬件身份应通过配置或可验证契约提供。

地址和中断等能力从真实 HWH 或明确的接口契约推导。版本相关修复独立标注条件；测得的超时参数保留测量条件及配置入口。

例如，相机 IRQ 编号、C6I GPIO 通道语义、当前编码器启动门限属于案例参数；元数据一致性校验、按连接核对语义、分开启动与稳态 deadline 属于可提炼方法。

## 5. ROSS 与本队 Skill 的关系

本机安装包元数据指向 `Xilinx/ross-ai-assistant`，版本 2026.9.1。ROSS 官方能力包括 Vivado MCP、AMD 文档检索以及 Vivado、Vitis HLS、硬件调试和 Vitis AI 等领域的 Agent Skills。

| 维度 | ROSS 官方能力 | 本队参赛增量 |
| --- | --- | --- |
| 主要任务 | 驱动工具、组织领域工作流、查询官方资料 | 沉淀 PYNQ 部署、运行安全、验证及应用开发方法 |
| 知识来源 | 官方方法、工具接口和示例 | 本队真实失败、观察、诊断与复验 |
| 可执行入口 | Agent Skills 和 MCP 工具 | 可独立执行的检查、测试、报告工具，以及 Agent 编排说明 |
| 工程实例 | 官方示例和支持范围 | 本队制品、用例、环境、原始回执与复用实例 |
| 贡献归属 | AMD 上游成果 | 本队新增的规则、配置、封装与验证材料 |

ROSS 本身也有通用 Skill。参赛材料应体现我们如何使用官方能力，以及在其基础上形成了哪些新增方法和证据。可以复用上游提示词或模板，并保留来源、版本、许可和修改说明。

推荐组织为“ROSS 等工具依赖 + 本队通用 PYNQ Skill + 本队项目应用 Skill”。运行时安装目录是工具装载位置；参赛提交以版本化源文件、说明和证据为依据。

## 7. 游戏设计 Skill 如何成为辅助成果

游戏设计 Skill 的价值在于把新玩法开发变成可重复流程，尤其适合保留以下方法：

| 可复用方法 | 对新项目的价值 | 建议证据 |
| --- | --- | --- |
| GamePlugin、GameInput 与 Scene 分层 | 新玩法沿用稳定输入和渲染合同 | 一个新游戏按模板完成实现和运行 |
| 固定 tick、seed 与确定性回放 | 快速复现输入顺序、边沿事件和状态机问题 | 同用例重复运行的输入、状态及 Scene 比对 |
| 双构建校验与同包测试 | 把源码、部署包与测试对象身份关联起来 | 双构建结果、包 SHA、用例与报告 |
| PC 预检、安装身份回读及部署门禁 | 提高装载过程的可审计性 | 实际安装回读及错误身份拒绝测试 |
| PC/板端软件报告对照 | 定位首个分歧 tick | 相同包和用例的报告，区分 PC、夹具与真实板端 |

game1 的横版移动、game2 的稳定手势猜拳、game3 的选角和声音机关，可作为框架承载不同任务的案例。案例应关联具体已验证的方法，而非仅展示完成的游戏画面。

适用范围可表述为“基于 Voice View Game SDK 与 Scene 合同的新体感游戏开发及验证”。这使陌生开发者能够判断是否适用于自己的项目，并按相同合同复用。

现有游戏 Skill 固定平台为 `0xC0060700`；融合候选为 `0xC0060800`。提交整理时需将两类身份、目标包配置和运行模式在说明中对齐，并引用当前打包与部署门禁。此分析文档保留现有实现，平台参数更新另行验证。

游戏设计与 Studio Skill 作为辅助章节，精选有复验依据的方法即可；通用 PYNQ 能力保持材料主线。

## 8. Studio 设计 Skill 的适用边界

现有 Studio Skill 已明确读取设计基线、沿用相邻测试、修改后立即局部验证，以及使用原生 PySide6 截图验收。

值得提炼的内容包括网络与 GUI 线程分离、不可变快照、历史数据状态、请求互斥、线程退出确认，以及区分 HTTP 图像、Agent 回执和真实硬件输出。

配色、固定布局和 Voice View 页面结构可作为项目案例保留。跨应用方法侧重线程生命周期、数据来源和验收流程；原生 Qt 实测、PC 软件测试与实板证据分别标注。

## 9. 通用 PYNQ 主线的优先方向

| 方向 | 已有来源 | 建议独立输入与输出 |
| --- | --- | --- |
| Overlay 制品预检与受控加载 | 配对哈希、邻接 XSA、IRQ 元数据、owner/borrower | 输入制品和硬件能力契约；输出预检报告、失败原因与清理回执 |
| DMA 与缓存、资源生命周期 | 缓存处理、deadline、停止确认和资源保留 | 输入通道能力、buffer 和超时配置；输出传输及清理结果 |
| 黄金参考与证据报告 | 来源校验、候选配对、包身份、场景回执 | 输入参考、运行结果和环境；输出可追溯的比对与指标报告 |

DMA、VDMA 和不同硬件接口分别定义适用合同。对特定版本解析器、运行 IPMap 或寄存器语义的处理，提供对应版本分支、能力检查与错误路径。

上述方向是后续提炼建议。当前项目中已有的实现与规则按现有证据引用；独立通用入口及跨板适配完成后追加相应验收结果。

## 10. 每项 Skill 的材料清单

建议每项提供以下信息，形成从来源到效果的可追溯链路：

1. 任务与适用场景：面向什么问题，在本题目之外还能用于哪些任务。
2. 支持条件：板卡能力、工具/PYNQ/Python 版本、权限、依赖和接口要求。
3. 使用入口：安装步骤、配置、输入输出、运行命令与预期结果。
4. 处理流程：检查顺序、停止条件、异常处理和人工恢复条件。
5. 验证材料：正常路径、代表性失败路径、原始回执与复验结果。
6. 提炼来源：具体失败或观察、提示词与纠错片段、最终规则的形成依据。
7. 复用效果：不同任务或平台的执行记录，明确实际验证范围。
8. 来源与许可：本队内容、上游依赖、修改内容和对应许可证。

推荐先完成陌生使用者按说明独立执行，再用同板不同任务检验题目解耦。有兼容第二块板卡时追加迁移实测，逐步扩展支持矩阵。指南中的通用性要求以真实验证支撑；具体测试数量和现场板卡数量按后续正式细则核对。

## 11. 来源与许可边界

公开 [ROSS skills 仓库许可证](https://github.com/Xilinx/ross-ai-assistant/blob/main/LICENSE)及本机 bundled plugin 为 MIT；复用时保留上游版权和许可声明，列出修改内容。

本机 Vivado AI Extension/MCP 本体采用单独的 Xilinx MCP Server and Extension License Agreement，其中包含再分发、基准测试结果披露等限制；适用独立开源许可的组件按各自许可证处理。

参赛材料优先提供官方工具安装链接、版本和环境说明，提交本队可分发的源码、方法及证据。对拟公开的协作记录和工具结果，结合对应许可、隐私和凭据脱敏要求核对。

> 基于 AMD ROSS 辅助开发，在 PYNQ 图像、音频与交互应用集成过程中提炼 Overlay 预检、DMA 生命周期和验证报告方法，并以游戏开发与 Studio 验收工作流展示工程复用效果。

使用该表述时，对其中各类任务和复用效果逐项给出已有证据；计划中的通用入口和迁移结果以待验状态管理。

建议执行顺序为：先整理最有证据的通用 PYNQ 流程，再加入少量游戏/Studio 辅助 Skill，随后完成独立使用和跨任务检查，最后扩展兼容板卡验证。

当前交付为分析文档。赛事指南快照、既有 Skill 源码与部署副本、硬件 ABI 和板端运行均保持现状；后续实际提炼由各项检查闭环推进。
